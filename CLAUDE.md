# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This repository is for work related to **CAT (Consolidated Audit Trail) reporting** for Industry Members, based on the FINRA CAT Technical Specifications v4.1.0 r15 (dated 3/6/2026) and v4.2.0 r2 (dated 9/23/2026; production 12/7/2026 per the 8/27/2026 IM release plan).

## Reference Specification

The primary reference document is the [CAT Reporting Technical Specifications for Industry Members v4.1.0 r15](https://www.catnmsplan.com/sites/default/files/2026-03/03.06.26_CAT_Reporting_Technical_Specifications_for_Industry_Members_v4.1.0r15_CLEAN.pdf). This ~63,000-line PDF covers:
- **CAT Reporting Fundamentals**: Order IDs, timestamps, order handling instructions, Firm ROE IDs, FDIDs, equity/option symbols, data types, and linkage rules
- **Special Reporting Requirements**: ATS reporting, manual orders, allocation events, RFQ responses, representative orders, combined orders, multi-leg orders, and more
- **Event specifications**: Detailed schemas for order lifecycle events (New Order, Route, Trade, Cancel, etc.) for both equities and options
- **File submission**: JSON file formats, connectivity (SFTP/AWS S3), feedback and error correction processes
- **Industry Member identifiers (IMIDs)** and **Firm Designated IDs (FDIDs)** are central concepts

When working with this spec, use `pdftotext` to extract relevant sections rather than reading the entire document. The v4.2.0 r2 spec is at https://www.catnmsplan.com/sites/default/files/2026-09/09.23.26_CAT_Reporting_Technical_Specifications_for_Industry_Members_v4.2.0r2_CLEAN.pdf (redline: same path with `_REDLINE.pdf`).

The official machine-readable schemas `03.18.26-IM-4.1.0-r15.json` and `08.14.26-IM-4.2.0.json` are in the repository root (untracked, like the spec PDF). They are the source of truth for the spec tables in `index.html`.

### Spec versions in the viewer
- The v4.1.0 r15 tables (CAT_SCHEMA, CAT_CSV_FIELDS, CAT_ARRAY_ELEMENTS, CAT_ALLOWED_TYPES, CAT_ALLOWED_EXCHANGES, CAT_CHOICE_VALUES) are the base. They match the r15 schema file exactly, except that CAT_ALLOWED_EXCHANGES and marketCenterID also include MX2OP/IEXOP (v4.2.0 values in production before the cutover).
- Later versions are a generated `CAT_SPEC_DELTAS` block (between `// <generated:spec-deltas>` markers) written by `node tools/gen-spec.js <base.json> <target.json>... --write`. Never hand-edit it; `tests/spec-tables.test.js` fails if it is stale. `applySpecDelta()` builds each version's tables into `CAT_SPECS` at load.
- `CAT_SPEC_VERSIONS` (hand-maintained) lists versions with their label, effective Eastern Time event date (`from`, YYYYMMDD), spec URL, and error codes they retire. `CAT_CODE_RETIREMENTS` holds codes retired mid-version (2247 from 20260601).
- `specForRecord()` picks the version from `recordEventDate()` (the ET date of eventTimestamp, else the firmROEID date, else tradeDate, else today), unless `specVersionSetting` forces one. That setting comes from Tools → Spec and is stored in localStorage `catViewer_specVersion`.
- `validateRecord(record, format, spec)` wraps `validateRecordAgainstSpec()` and drops retired codes. In CSV, fields removed in a later version keep their base-layout names and are flagged as retired positions (2207); in JSON they are flagged as not part of the event (2133). Removed event types (e.g. MONQ in v4.2.0) get 2105. CSV parsing always uses the base layout; `tools/gen-spec.js` refuses to generate a delta if a later version moves a field instead of retiring its position.
- Validated records carry a non-enumerable `_specVersion`. The header `#specLink` lists the versions applied (`updateSpecLabel()`), and the detail panel title shows the record's version.

## CAT File Viewer (`index.html`)

A single-file web application for compliance officers to inspect CAT data files. No build step required — open `index.html` directly in a browser.

### Key features
- Drag-and-drop or file picker for JSON (NDJSON), CSV, BZip2, ZIP, and GZIP format CAT files (multiple files supported; hold Shift to append). `handleFiles()` queues loads so files are processed one at a time in order (concurrent reads used to let a replacing load finish last and silently discard appended files); `handleFile()`/`processFileText()` resolve/return whether records were loaded. Each record gets a non-enumerable `_format` (via `setRecordMeta()`, alongside `_lineBytes` for the 2132 line-length check) and `deferValidation()` validates each record with its own format, so CSV and JSON files can be mixed. CSV delete lines (`DEL,errorROEID,firmROEID`) parse to just those fields, and trailing delimiters are ignored
- Auto-detects format from extension and content; validates files are CAT format before loading
- Sortable, paginated record table with multi-column sort (Shift+click), 3-state cycle (asc/desc/unsort), priority column ordering, and configurable page size (50/100/250/500/All)
- Column manager to show/hide/reorder columns, with search highlighting and layout persistence
- Sticky header that stays visible while scrolling
- Dynamic searchable filters with collapsible comboboxes, range support, and layout persistence
- Filters by event type (with detailed descriptions), action type (NEW/RPR/COR/DEL), side, error code, and free-text search; default filters include type, symbol, underlying, and optionID
- Color-coded event type badges (order/route/trade/cancel/modify/quote/allocation)
- Fixed, resizable record detail panel at bottom of viewport with animated slide-up/down transitions and translated/original view modes
- Translated display for timestamps (both string format and epoch nanoseconds → Eastern Time), dates, side codes, compound fields (legDetails, buyDetails, sellDetails, clientDetails, firmDetails)
- Side-slot virtual columns: `flattenSideSlots()` flattens the first element of side-detail compound arrays into positional `side1.*` (buy/client) and `side2.*` (sell/firm) columns so trades and fulfillments line up in the same columns; emission is deterministic per event type (driven by CAT_ARRAY_ELEMENTS) so `discoverColumns()`'s one-record-per-type sampling always finds the keys. All slot subfields are visible by default, grouped per slot in PRIORITY_COLUMNS after tradeID; the orderID cells carry a role chip (B/S/C/F for the source array) and a "+N" chip when the array has extra elements. The raw compound columns are in DEFAULT_HIDDEN_COLUMNS — hidden unless the saved column order already knows the column (so saved layouts keep user choices). Slot columns behave as regular columns (sort/filter/search via combobox, CSV export, orderID linkage) and surface their source field's validation errors at the cell level; they are excluded from `_searchText` (values duplicate the compound field), the detail panel, and the Raw Data tab. Slot metadata lives in `record._sideSlots`
- Name/Value Pair columns: `flattenRecord()` turns handlingInstructions, bidRelativePrice, and askRelativePrice (NVP_FIELDS) — JSON objects or pipe-delimited CSV strings, parsed by `parseNameValuePairs()` — into a summary column in spec CSV notation (`ALG|DISQ=100|DLVT=MM1@MM2`, same for both formats) plus per-attribute `<field>.<attr>` columns. Attribute sets vary per record, not per type, so `discoverColumns()` scans every record for NVP columns (once per distinct summary value) instead of relying on its one-record-per-type sampling. The summary column is in PRIORITY_COLUMNS after timeInForce.value; attribute columns are hidden by default (`isDefaultHiddenColumn()`), excluded from `_searchText`, the detail panel, and the Raw Data tab, and only surface validation errors naming their own attribute. The detail panel's Original mode shows the raw reported value from `_original`. Validation and the CASH check (2247) share `parseNameValuePairs()`; in CSV a Boolean attribute with a value (e.g. `AOK=true`) is an error
- `escapeHtml()` escapes `& < > " '` and is safe inside quoted attributes (data-link-value, title, data-tooltip, data-col). ID-keyed indexes (idIndex, orderIndex, chain byOrder, summary counts) and the value-keyed lookup tables (EVENT_CATEGORIES, FIELD_LABELS, FIELD_TOOLTIPS, CAT_SCHEMA, CAT_CSV_FIELDS, CAT_ARRAY_ELEMENTS, CAT_CHOICE_VALUES, LINKAGE_FIELDS, SIDE_SLOT_ROLES) have null prototypes, so values like `constructor` or `toString` don't resolve to Object methods
- Clickable linkage fields (orderID, tradeID, fulfillmentID/priorFulfillmentID, allocationID/priorAllocationID, quoteID/routedQuoteID/receivedQuoteID, RFQID, parentOrderID, priorOrderID, routedOrderID, etc.) for navigating between related records; clicking clears other active filters. routedOrderID/priorRoutedOrderID target the `routedOrderID` index (both sides of a route), not orderIDs. Events without a top-level orderID (Order Trade / Order Fulfillment: MEOT, MEOTS, MOOT, MEOF, MEOFS, MEFA, MOOF, MOOFS, MOFA) are linked to orders via the orderIDs inside their side details (buyDetails/sellDetails/clientDetails/firmDetails). Nested orderID linkage is type-agnostic: `getNestedOrderIDs()` extracts orderIDs from any compound array field on any event type (side details plus aggregatedOrders/askAggregatedOrders/bidAggregatedOrders, in both JSON array and CSV string form), and `getRecordLaneOrderIDs()` resolves a record's effective orderIDs from it — used by the ID index, order chain views, and timeline lanes. The orderID filter matches nested orderIDs too, so filtering by an order ID includes its trade/fulfillment events (e.g. MENO/MECO/MEOR and the MEOT trades referencing the same order), and the orderID filter dropdown lists orderIDs that appear only inside compound arrays. Free-text search covers nested compound field values.
- Order identity (Order Keys): `buildOrderIdentity()` (called from `buildOrderIndex()`) collects every order reference in `orderReferences()` (own, parent, prior, manual, nested items from `getNestedOrderItems()`) and keys it on reporter, normalized key date (exact ns via the memoized `normalizeKeyDate()`, so epoch and string forms match), instrument (`recordInstrument()`: symbol, else optionID, else none for multi-leg), and orderID. An orderID with one Order Key keeps its orderID as its **node ID**. An orderID with several gets qualified node IDs like `ORD1 (2025-03-18)`, `ORD1 (AAPL)`, or `ORD1 (2025-03-17 09:30:00.000)`, naming only the parts that differ. orderIndex, `getRecordLaneOrderIDs()`, chain views, `orderChainRoot` / the URL `chain=` value, and timeline lanes all use node IDs. `resolveOrderNode()` maps a reference without a key date to the only matching order, else to the plain orderID. Link cells carry `data-link-node` from `linkOrderNode()` (side-slot orderIDs pair with the same slot's orderKeyDate; nested detail tables pass the element), and `handleLinkClick()` enters that node's chain. Raw orderIDs are still used for the ID index, the orderID filter, and search (`getNestedOrderIDs()`)
- Corrections: `buildCorrections()` (from `buildOrderIndex()`) matches COR/RPR/DEL records to the record in effect for the same firmROEID (and CATReporterIMID, which DEL records usually omit; they then match when only one reporter used the firmROEID). It records supersededBy/deletedBy/replaces/deletes in a WeakMap read through `correctionInfo()`; `isEffectiveRecord()` is false for replaced or deleted records and for DEL instructions. Tools → Apply Corrections (`effectiveViewEnabled`) filters the pool in `applyFilters()`; rows not in effect get `row-superseded` and a `correctionNote()` chip; the detail title links related records
- Cross-record checks: `crossRecordChecks(records)` runs after chunked validation in `deferValidation()` and merges its errors into `r._errors`. `EVENT_KEY_KINDS` defines each Event Key: primary types, and derived types that assign a new key through a parent/prior reference that differs from their own key. It reports 3002 (NEW records only), duplicate keys (3004/3010/3012/3016/3020), 3501 (warn: a key not assigned by any loaded event), 3601 (50 ms, or 1 s if either event is manual), 3502–3504 (warn, from `NESTED_ORDER_REF_CODES`), 3602 (`SUPPLEMENT_PARENTS`, millisecond precision), and 3711 (PENDING FDID not resolved by a `FDID_SUPPLEMENT_TYPES` supplement). Superseded/deleted records are excluded
- Order chain view with hierarchy tree, depth controls (This order, + Children, + Branch) that toggle off when clicked again; + Children shows all descendants; Branch shows direct ancestor chain plus descendants, excluding siblings. Chain ordering compares timestamps with `catTimestampToNs()` (exact BigInt UTC nanoseconds from ET strings or epoch numbers), so numeric eventTimestamps no longer crash the chain and mixed formats order by instant. When events in an order group share a timestamp, order-origination events (MENO/MEOA/MECO/MEIR and options/multi-leg equivalents) sort first, then their supplements (MENOS/MONOS/MLOS), then other events
- URL hash state with deep linking to selected records
- Tools dropdown menu (keyboard shortcut accessible) with layout export/import, drag-and-drop layout reordering, validation toggle, and performance panel toggle. Reset Layout followed by Save Layout clears saved layout so defaults are always used.
- Performance panel (Tools menu toggle): floating overlay showing timing stats (last/avg/count) for critical paths (parse, flatten, validate, filter, sort, column widths, timeline build/draw). Auto-refreshes every 500ms. Zero overhead when disabled.
- Virtual scrolling for large datasets with sub-pixel-accurate column width locking (samples longest values per column to prevent clipping)

### CAT file format notes
- **JSON files**: NDJSON (one JSON object per line) or a JSON array. Each record has a `type` field (e.g., `MENO`, `MEOR`, `MEOT`) and `actionType` (`NEW`, `RPR`, `COR`, `DEL`).
- **CSV files**: Positional fields with no header row. Field position 4 (0-indexed 3) is always `type`. The viewer maps all 99 event types (39 equity ME, 35 options MO, 25 multi-leg ML) to named fields per the spec, with each type having its own distinct field schema.
- **ZIP/GZIP/BZip2**: ZIP archives containing JSON or CSV files (optionally `.gz`/`.bz2` inside; stored, deflate or bzip2 entries); GZIP- and BZip2-compressed files (`.json.gz`, `.csv.bz2`, …). All decompressed in-browser. `listZipEntries()` reads the central directory (and the ZIP64 end record and 0x0001 extra field), never local-header sizes, because streaming writers leave them zero. `handleZipFile()` reports a failing entry with `showWarning()` and keeps going. `bunzip2()` is a self-contained decoder with block and stream CRC checks that handles concatenated streams. Randomized blocks (pre-0.9.5 bzip2) are rejected.
- **Exact numbers**: `parseJSON()` goes through `parseJSONLossless()`. Number tokens with more than 15 significant digits are rewritten to sentinel strings by `quoteLongNumbers()`, then turned back into exact decimal text by `losslessReviver()`, which records the holder object and key in the `_losslessNumbers` WeakMap. Validation accepts those as JSON numbers via `isLosslessNumber()`. The Raw Data tab prints them unquoted with `JSON.rawJSON` where available. `plainNumberText()` expands exponent notation, and `formatDecimalText()` formats prices and quantities from text. `getComparableValue()` returns BigInt for 16+ digit integers and exact ns (`catTimestampToNs`) for timestamp columns. The table sort precomputes timestamp keys per record, `getColumnType()` is cached per `allRecords` array, and range bounds are computed once per filter.
- **Skipped lines**: `parseJSON()` returns an array with `skippedLines: [{line, message}]`. `processFileText()` reports them through `showWarning()` (an orange message bar; warnings from one batch accumulate, and `handleFiles()` clears the bar once per batch). An uncompressed file larger than `MAX_TEXT_CHARS` is refused up front, and `describeReadError()` explains the browser string-size limit when decompression runs out of room.
- Event type prefixes: `ME` = equity, `MO` = option, `ML` = multi-leg

### Versioning
Version is automatically set by a git pre-commit hook (`.git/hooks/pre-commit`). Format: `vYYYY.MM.DD`. Do not manually set version numbers in `index.html`.
